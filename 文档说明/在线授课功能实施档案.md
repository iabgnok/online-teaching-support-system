# 在线授课功能实施档案

## 功能概述
根据《功能与 UI 更新指导文档》，在线授课协同模块是系统的核心功能之一。该模块整合屏幕共享、实时画板与文字互动于一体的协同界面，支持教师以教学班为单位发起在线授课，学生通过专用入口进入课堂。核心特性包括画板协同（基于 Flask-SocketIO 的实时同步）、媒体流（WebRTC 屏幕共享）、课堂管理和自动生成课堂笔记。

## 业务流程描述
在线授课功能从教师发起到课堂结束的全业务流程如下：

1. **教师发起授课**：教师登录系统，选择特定教学班，点击“开始在线授课”按钮。系统验证权限后，创建课堂会话（LessonID），并自动发布一则“授课开始通知”公告至该教学班的所有学生。

2. **学生加入课堂**：学生收到公告通知，通过导航栏的“上课页面”入口进入课堂。系统验证学生身份，确保仅该教学班成员可加入。

3. **课堂初始化**：教师端加载控制面板，包括屏幕共享开关、画板工具栏和聊天区域。学生端加载观看界面，包括实时画板显示、屏幕共享视频窗口和聊天输入框。所有参与者通过 SocketIO 连接到课堂房间。

4. **屏幕共享启动**：教师点击屏幕共享按钮，使用 WebRTC 捕获并广播屏幕内容。学生端实时接收并显示共享视频。

5. **画板协同互动**：教师在画板上进行绘制（涂鸦、标注等），系统使用百分比坐标通过 SocketIO 实时同步到所有学生端。学生可观看但不可编辑（除非教师授权）。

6. **文字互动**：教师和学生可在聊天区域发送文字消息，消息实时广播至所有参与者。

7. **课堂管理**：教师可在授课过程中便捷下发任务（作业）或进行考勤检查。任务和考勤数据自动计入原有统计模块。

8. **授课结束**：教师点击“结束授课”按钮。系统停止所有实时连接，汇总课堂互动信息（画板坐标、聊天记录、任务/考勤数据）生成“课堂笔记”。

9. **笔记发布**：教师审核生成的课堂笔记，选择是否发布给学生。若发布，笔记将作为公告或材料存储在系统中供学生查看。

10. **数据持久化**：所有互动数据（坐标、消息、笔记）与 LessonID 关联存储在数据库中，便于课后回溯和分析。

整个流程强调实时性、安全性和集成性，确保教师高效授课，学生沉浸式学习。

## UI设计描述
参考Moodle学习管理系统的UI风格，在线授课页面的设计采用响应式布局、模块化组件和直观图标，确保用户友好和高效互动。整体遵循Moodle的卡片式设计、悬浮导航和颜色主题。

### 整体布局框架
- **左侧导航栏**：竖向排列，初始状态仅显示图标（悬浮压缩态），鼠标悬停展开显示文字。包括“上课页面”入口、其他模块链接。底部显示用户头像和身份（教师/学生）。
- **顶部工具栏**：显示课堂标题（教学班名称）、当前时间、参与者数量。教师端额外显示“结束授课”按钮。
- **中央内容区域**：主要互动区，占据大部分屏幕空间。使用白色背景、阴影边框的卡片容器。
- **右侧面板**：可选展开的侧边栏，用于工具和设置。
- **底部区域**：聊天输入框和消息列表。

### 教师端页面UI
- **中央画板区域**：Canvas画板占据中央，教师可自由绘制。工具栏位于画板上方，包括笔刷、颜色选择器、擦除、撤销/重做按钮。支持全屏模式。
- **屏幕共享控制**：顶部工具栏右侧按钮，点击启动/停止屏幕共享。共享时，画板下方显示共享预览窗口。
- **聊天区域**：底部固定区域，消息列表滚动显示，输入框支持表情和文件附件。教师消息高亮显示。
- **课堂管理面板**：右侧可展开面板，包括“下发任务”按钮、“考勤检查”按钮。任务下发弹窗选择作业类型和截止时间。
- **参与者列表**：右侧面板显示在线学生列表，支持私聊或踢出功能。
- **响应式设计**：在小屏幕上，右侧面板折叠，画板自适应缩放。

### 学生端页面UI
- **中央观看区域**：上方显示屏幕共享视频（WebRTC流），下方显示实时画板。视频可全屏，画板同步教师绘制。
- **聊天区域**：右侧固定面板，消息列表和输入框。学生消息正常显示，支持@教师。
- **工具栏**：顶部显示课堂信息，右侧有“举手”按钮（请求发言）和“退出课堂”按钮。
- **互动反馈**：画板下方有“点赞”或“提问”按钮，点击发送表情或快速消息。
- **响应式设计**：移动端时，聊天面板折叠为底部弹窗，视频和画板垂直堆叠。

UI设计强调一致性，使用系统变量色（如绿色表示正常，红色表示警告），图标采用Material Design风格。所有组件支持键盘快捷键，提升操作效率。

## 技术栈分析
- **后端**：Flask-SocketIO（用于实时通信和画板同步）、WebRTC（用于媒体流传输）、Flask（现有框架扩展）。
- **前端**：Vue.js（现有框架）、Canvas API（画板绘制）、WebRTC API（屏幕共享）、Socket.IO 客户端（实时同步）。
- **数据库**：SQL Server（存储课堂笔记、聊天记录，与 LessonID 关联）。
- **其他**：百分比坐标系统（适配不同分辨率）、时间戳机制（处理网络延迟）。

## 技术难点分析
在线授课功能涉及实时协作、多媒体传输和大规模并发，存在以下技术难点及应对策略：

### 1. 实时画板同步
- **难点**：Canvas坐标在不同分辨率设备上需精确同步，使用百分比坐标避免偏移，但网络延迟可能导致绘制顺序错乱或丢失。
- **应对**：实现时间戳机制，客户端接收数据时按时间戳排序重放；添加确认机制，确保关键绘制点同步；使用WebSocket压缩减少数据量。

### 2. WebRTC媒体流传输
- **难点**：屏幕共享涉及信令服务器搭建、NAT穿越（STUN/TURN服务器）、浏览器兼容性（Chrome/Firefox差异）、带宽限制导致视频质量下降。
- **应对**：集成开源WebRTC库（如PeerJS），部署TURN服务器处理复杂网络；实现自适应码率，根据网络状况调整分辨率；添加备用模式（如纯音频或静态图片）。

### 3. SocketIO实时通信
- **难点**：大规模并发（50+用户）时，服务器负载高，消息广播延迟；网络不稳定导致连接断开和重连。
- **应对**：使用Redis作为SocketIO消息队列，实现水平扩展；实现心跳检测和自动重连机制；优化消息格式，减少不必要广播。

### 4. 状态同步与冲突解决
- **难点**：教师切换屏幕共享或画板内容时，多客户端状态不一致；网络延迟导致操作顺序错乱。
- **应对**：引入操作日志和版本控制，每个操作带唯一ID和时间戳；服务器端维护权威状态，客户端定期同步；使用乐观锁处理冲突。

### 5. 安全与权限控制
- **难点**：防止未授权用户加入课堂、数据泄露；实时传输中加密开销。
- **应对**：JWT令牌验证用户身份和角色；WebRTC使用DTLS加密传输；服务器端过滤消息，确保仅课堂成员接收。

### 6. 性能与可扩展性
- **难点**：高并发下数据库写入频繁（聊天、坐标数据），可能导致瓶颈；前端Canvas渲染在低端设备上卡顿。
- **应对**：使用异步队列处理数据持久化；实现Canvas虚拟化，仅渲染可见区域；部署CDN加速静态资源，负载均衡服务器。

### 7. 跨平台兼容性
- **难点**：不同浏览器和设备对WebRTC/Canvas支持差异；移动端触摸操作与桌面鼠标不一致。
- **应对**：Polyfill库填补兼容性差距；响应式设计适配触摸；测试矩阵覆盖主流环境。

### 8. 数据持久化与回放
- **难点**：实时数据量大（坐标序列、视频流），存储和回放复杂；生成课堂笔记需智能汇总。
- **应对**：分层存储（实时数据缓存，回放数据压缩）；使用AI/ML分析互动生成摘要；支持录制回放功能。

这些难点需前期原型验证和性能基准测试，确保功能稳定可靠。

## 实施步骤
1. **需求确认与设计**
   - 分析现有系统架构，确保与教学班、公告、任务和考勤模块的集成。

   - 定义数据模型：课堂会话表（LessonID、开始时间、结束时间）、互动记录表（坐标数据、聊天消息）。

   - 集成 Flask-SocketIO：实现画板坐标同步、状态广播。

   - 添加 API 端点：发起授课（发布公告）、结束授课（生成笔记）、下发任务/考勤。
   - 持久化逻辑：将互动数据存储到数据库。

3. **前端开发**
   - 创建“上课页面”视图：教师端和学生端分别实现。
   - 实现画板组件：使用 Canvas，支持绘制、擦除，发送百分比坐标。
   - 集成 WebRTC：教师端捕获屏幕，学生端接收并显示。
   - 添加聊天功能：实时文字互动。
   - 响应式设计：适配不同设备分辨率。

4. **集成与测试**
   - 与现有模块集成：公告发布、任务下发、考勤统计。
   - 单元测试：SocketIO 连接、WebRTC 传输、数据库存储。
   - 端到端测试：模拟教师发起授课、学生加入、协同绘制、生成笔记。

5. **部署与上线**
   - 更新导航栏：添加“上课页面”入口。
   - 文档更新：补充用户手册和技术文档。
   - 培训：为教师和学生提供使用指导。

## 隔离开发指导
为降低耦合风险，提高开发效率，在线授课模块采用隔离开发策略，确保与其他系统模块（如公告、任务、考勤）独立演进。以下是详细指导：

### 1. 模块边界定义
- **接口化**：定义清晰的API接口，与外部模块通过RESTful API或消息队列交互。例如，发起授课时调用公告模块的发布接口，下发任务时调用任务模块的创建接口。
- **依赖最小化**：仅依赖核心认证和用户管理模块，避免直接耦合业务逻辑。
- **数据隔离**：课堂数据存储在独立表中，通过LessonID关联，不修改现有表结构。

### 2. 代码组织
- **后端**：创建独立包`live_class`，包含`api.py`（端点）、`socket_handlers.py`（SocketIO逻辑）、`webrtc_server.py`（信令服务器）。使用Blueprint注册到主应用。
- **前端**：在`src/modules/liveClass/`下组织组件，避免直接修改全局路由。使用Vuex独立状态管理课堂数据。
- **数据库**：新增迁移脚本`migrate_live_class.py`，独立执行，不影响现有数据。

### 3. 版本控制策略
- **分支管理**：创建`feature/live-class`分支，隔离开发。定期从主分支合并更新，避免冲突。
- **代码审查**：使用Pull Request，确保隔离代码不引入全局依赖。
- **标签版本**：模块开发完成后，打标签如`v1.0-live-class`，便于回滚。

### 4. 开发环境搭建
- **虚拟环境**：使用Python venv隔离依赖，安装专用包如`flask-socketio`、`aiortc`（WebRTC）。
- **本地服务器**：运行独立Flask实例，端口不同（如8001），前端使用代理转发API调用。
- **模拟数据**：前期使用Mock数据模拟公告、任务接口，避免依赖完整后端。

### 5. 测试策略
- **单元测试**：针对模块内函数，如坐标同步算法、SocketIO事件处理。使用pytest，覆盖率>80%。
- **集成测试**：模块内部组件测试，如画板+聊天组合。使用Selenium或Playwright模拟用户操作。
- **端到端测试**：在隔离环境中运行完整流程，验证与外部接口的Mock调用。
- **性能测试**：使用Locust模拟并发用户，监控延迟和资源使用。

### 6. 集成与部署
- **渐进集成**：先集成认证模块，再逐步添加公告、任务等。使用Feature Toggle控制新功能上线。
- **容器化**：使用Docker封装模块，便于独立部署和扩展。Compose文件定义服务依赖。
- **监控与日志**：集成ELK栈，独立监控模块性能，避免影响主系统。

通过隔离开发，可并行推进，降低风险，确保高质量交付。

- **功能测试**：验证画板同步、屏幕共享、聊天、任务下发。

## 风险评估
- **技术风险**：WebRTC 在某些网络环境下的兼容性问题；SocketIO 的实时性依赖网络质量。
- **实施风险**：与现有系统的集成可能引入冲突；教师/学生培训不足导致 adoption 低。
- **缓解措施**：前期原型验证；提供备用方案（如纯文字模式）；详细文档和培训材料。
